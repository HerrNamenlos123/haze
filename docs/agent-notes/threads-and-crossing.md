# Threads, the crossing rule and atomic data

Where threads, the crossing rule and the atomic types live, how the standard library's thread tools cross, and the traps found building on them.

Verified 2026-11-27 against the sys.cpuCount commit on async-runtime (its parent: 2e502c7e).

**Files:** `stdlib/core/src/thread.hz` (`thread.spawn`, `SpawnOptions`), `task.hz` (`Future<T>`, `_FutureCore`), `sync.hz` (`sys.Mutex`, `sys.Flag`), `memory.hz` (`AtomicArena`, `Alloc.atomicArena`, `AtomicTypeErasedBox`), `hzstd_sched.c` ("thread.spawn", cores and their spin lock `hzstd_core_lock`), `hzstd_memory.c` ("Atomic arena"), `src/Semantic/Crossing.ts` (the rule). Tests: `testsuite/src/cases_threads.hz`, `cases_crossing.hz`, `cases_atomic.hz`; stress: `scripts/thread-stress.sh` (not in the gate). Decisions: `docs/async-decisions.md` S5-*, S5-R*, S5-C*, S5-I*. Contract: `docs/async-runtime.md` section 2.

- `thread.spawn` takes `crossthread () => T`: every capture and the result must cross (H7238). Shared data is atomic: atomic structs, `atomic []T`, or the self-locking tools (`sys.Mutex`, `sys.Flag`, `Future<T>` when T crosses, `AtomicArena`, `AtomicTypeErasedBox`). A plain `[]T`, a plain `ref struct`, `Arena`, `TypeErasedBox`, the context never cross.
- A thread returns an array it built only as `mut atomic []T`: a plain array never crosses, and only an array literal converts to an atomic one, so declare it atomic where it is made.
- An atomic array's every operation takes the array's own lock and is a suspension point (S5-9), so a `lockWhen`/`waitUntil` condition cannot read one (it panics: "This call can suspend"). Data a mutex guards goes into an atomic struct as `private unsafe` fields touched only under that mutex (C172), the mutex in a `private` field (a public one can be replaced; `const` would make the mutex const data); conditions read those without suspending. Examples: `Jobs` in cases_threads.hz, `WorkQueue` in examples/async.
- Trap: a crossthread conversion inside a method of a generic struct rejects every instantiation whose T does not cross, because a struct's methods are elaborated for every instantiation (see order-dependent-struct-method-elaboration.md). `Future<Plain>` failed as a mere type alias while a Future method built a crossthread thunk; thread.spawn builds it (S5-I2).
- Trap: an error inside a generic function's body is reported before, and instead of, the error of the call's own argument conversion, with no reference to the call; for a stdlib generic it points into `__haze__/haze-stdlib/build/import.hz` (probes, 2026-11-26, a user-module generic too). So when what a thread body returns does not cross, the H7238 names thread.spawn's own closure (its capture `me`).
- Every entry point that runs code on a new thread takes a `crossthread` closure (`_FutureCore.spawnThread`); an exported function or public method that hands a plain closure to another thread is a hole in the crossing rule, whatever its name (the review of 2026-11-26 found two). The same for an `unsafe crossthread` struct with a public pointer field: it carries any pointer across, so such wrappers are opaque.
- `AtomicTypeErasedBox<T>(value)` needs its type argument written out (a generic constructor's argument is not deduced, as for `TypeErasedBox<int>(5)`); it asserts `T.isAtomic && T.crossesThreads` (an atomic `Future<Plain>` does not cross). Store and read with the same T (`mut Stats` and `Stats` are different fingerprints; writing an atomic field needs `mut`).
- `atomic` primitives (`n: atomic int`) are fields or globals only; `c.n = c.n + 1` is two atomic steps (a logical race, allowed), `c.n += 1` one.
- The atomic arena locks only to bump and to install a chunk; chunks are made outside the lock (making one can panic). A plain arena's chunks go through `hzstd_arena_make_chunk` then `hzstd_arena_link_chunk`, the same steps as before the split. The struct starts with its `hzstd_arena_t`, so `(hzstd_arena_t *)allocator.ctx` reads either kind's chains.
- Racing threads: a wake-up (Flag, future) reaches waiting threads one after the other, too slowly to make their next steps collide; a test that needs a race lets threads spin on an atomic field (the first-chunk case in cases_threads.hz). A race that only wastes or misplaces memory hands nothing out twice, so marks and usage miss it: check the chain itself (it ends at its tail, the chunks' used bytes add up).
- `sys.cpuCount()` (system.hz, `hzstd_cpu_count` in each platform file): the calling thread's affinity, lowered by the lowest cgroup CPU quota (v2 and v1) on its cgroup or above, rounded up; Windows adds a job object's hard cap (S5-I9). `nproc` and `os.cpus()` ignore quotas: under `systemd-run --user --scope -p CPUQuota=150%` nproc says 16 here, cpuCount 2. Real quotas need no root: `systemd-run --user --scope -p Delegate=yes -p CPUQuota=...` (the cpu controller is delegated to user@.service here; the scope is removed when the command ends, sub-cgroups included). `hzstd_cgroup_cpu_limit` takes the /proc file paths and a root, so tests hand it made-up trees (cases_cpu_count.hz).
- Every task of every thread has the default stack (8 MiB reserved, committed as touched): there is no stack size option (S5-R4).
- Windows: built and run 2026-11-27 against 606eb894 plus the watchdog start fix (decisions W-1 to W-3): the thread, crossing, atomic and cpuCount cases pass in the gate, `scripts/thread-stress.sh` is exact (5 runs of 60 s, 393 rounds), examples/async runs. Trap: two calls with side effects in one f-string or call run right to left on Win64; a case that needs their order reads them into `let`s first.
