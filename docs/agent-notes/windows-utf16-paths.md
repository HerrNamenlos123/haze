# Windows: UTF-16 calls, long paths, error texts

How hzstd hands Haze's UTF-8 text to Windows, what long paths can and cannot do there, and how Windows failures are reported.

Verified 2026-11-24 against main 1514df64 (Windows 11, x64, LongPathsEnabled=0).

- Every Win32 call in the repo's own C is the UTF-16 `...W` variant; an `...A` call reads UTF-8 in the ANSI code page, so names outside it ("日本", "✓") are created garbled on disk and only other ANSI calls find them again. Windows builds define `UNICODE`/`_UNICODE` (`ModuleCompiler.ts`, next to `-DHAZE_PLATFORM_WIN32`), so macro names resolve to `...W`; `scripts/no-ansi-win32.test.ts` (in the gate, any platform) fails on an ANSI name written out (`FooA(`, dbghelp's `SymInitialize`/`SymFromAddr`/`SymGetLineFromAddr64`, `SYMBOL_INFO`, `STARTUPINFOA`, `CP_ACP`). Third-party libraries (bdwgc, libuv, SDL3, the prebuilt wgpu-native) still import ANSI functions; `llvm-nm <lib> | grep __imp_.*A` lists them. Decided 2026-11-24: left for now, patched later.
- The one conversion place: `stdlib/core/src/hzstd/include/hzstd_win_utf16.h` (`hzstd_win_utf16`, `hzstd_win_utf8`, `hzstd_win_utf8_into`). Paths for the fs calls go through `hzstd_win_path` (`hzstd_filesystem.c`): absolute via `GetFullPathNameW` (also turns `/` into `\` and resolves `.`/`..`), always `\\?\`-prefixed (`\\?\UNC\` for `\\server\share`), so short and long paths behave the same and a trailing dot or space stays part of the name. `moveToTrash` is the exception: `SHFileOperationW` takes no prefix.
- Measured with a C probe: `...W` without the prefix fails past MAX_PATH (error 3); with it a 655-character folder and file work. A working directory past MAX_PATH is impossible: `CreateProcessW` fails with 267 and `SetCurrentDirectoryW` with 206, with or without the prefix. The spawner reports such a cwd as `ERROR_FILENAME_EXCED_RANGE` ("File name too long") before trying (`process_spawn_inputs`, `hzstd_platform_win32.c`).
- A Win32 error becomes an errno (`hzstd_fs_errno_from_windows_error`) and then takes the Linux way to the error code and text: the same condition gives the same code and the same static glibc text on both platforms (`hzstd_fs_errno_text`), nothing allocated. A failed spawn's message is that text too.
- Opening a folder as a file is refused as access denied on Windows; hzstd reports it as NotAFile (readHead, openRead) and as AlreadyExists for createText, as on Linux.
- `fs.readText` opens in text mode on Windows (`"r"`, kept as before): CRLF is read as LF and a 0x1A byte ends the file, Linux returns the bytes. Decided 2026-11-24: runtime text reads normalize line endings on both platforms, like source code; not built yet.
- The command line (`hzstd_win_cmdline.h`) quotes an argument that is empty or holds whitespace or a quote, so `CommandLineToArgvW` in the child gives back exactly the arguments; covered by `cases_runtime_scratch_strings`.
