# Where wgpu blocks for vsync, and which locks couple threads

Research for taking the vsync wait off Haze's event loop: the wait is in acquire, and the locks wgpu holds while it blocks decide which other threads stall.

Verified 2026-11-23 against main 247774be (pin unchanged: wgpu-native 768f15f6 = wgpu-core 27.0.3, stdlib/wgpu/scripts/build-wgpu.hz) and upstream sources read that day: wgpu v30.0.2, and wgpu-native PR #630 head 8322fe1a, which pins wgpu trunk 1a3a4cc2 (2026-07-27, 105 commits past v30.0.0; acquire, present and poll match v30.0.2). The v27/v29 and platform facts are from sources read 2026-10-18, not re-read.

- Haze today: renderer.hz `Canvas.currentView` acquires lazily on the UI thread (the vsync wait blocks it); `present` then releases view and texture (~1436-1484). app.hz defaults to Fifo and tries Vulkan/Metal/DX12 before all backends, GL included (~279-313). Outside stdlib/wgpu only renderer, app, sdl_wgpu, glfw_wgpu and one codeeditor file call wgpu (grep).
- The wait is in `getCurrentTexture` (hal `acquire_texture`), not `present`. wgpu-core passes `FRAME_TIMEOUT_MS` = 1000 ms; webgpu.h has no timeout, so acquire cannot be polled. Vulkan: fence wait for the semaphore's previous use, `vkAcquireNextImageKHR`, fence wait.
- Platforms (2026-10-18): Mesa Wayland with wp_fifo_v1 (Mutter 48): present does not block, acquire waits for a released buffer; without fifo-v1 Mesa blocks in present on the frame callback. GL blocks in eglSwapBuffers. DX12 waits on the frame-latency waitable in acquire (hal `waitable_handle()`, not in wgpu.h). Metal blocks in nextDrawable.
- v27 and v29 hold `device.fence.read()` across acquire and `queue.submit` needs `fence.write()`: submits on other threads wait for vsync. v30 removed that lock (PR #9475).
- v30 acquire holds nothing device-wide: wgpu-native's per-surface `surface.data` mutex for the whole call (lib.rs `wgpuSurfaceGetCurrentTexture`) and hal's per-surface swapchain write lock (vulkan instance.rs, dx12 mod.rs). Only calls on the same surface wait.
- v30 present (present.rs `Queue::present`): `snatchable_lock.write()` briefly, then `command_indices.write()` across the HAL present, so every submit on every thread waits while vkQueuePresentKHR or DXGI Present runs (up to a frame where present blocks). GL holds its one context mutex across eglSwapBuffers (egl.rs present): with Fifo every GL call on every thread waits for vsync.
- v30 `wgpuDevicePoll(wait)` holds `snatchable_lock.read()` across the fence wait (resource.rs `poll_and_return_closures` -> `maintain`); still so on trunk 2026-11-23. Surface configure waits for GPU idle the same way (`configure_surface`); trunk #10675 (2026-11-20) also holds `command_indices` around the HAL configure. The lock is parking_lot's task-fair RwLock (lock/vanilla.rs): a waiting writer queues every later reader. Writers: present, buffer/texture destroy. Readers: submit, writeBuffer, writeTexture, encoder finish, ~28 sites. A thread blocked in poll(wait) or configure therefore stalls any present or destroy and, behind it, every submit on every thread.
- wgpu-native (port): releasing a surface texture (`WGPUTextureImpl` Drop) locks `surface.data`. Before present it discards the frame; after present it waits while another thread is in the next acquire. Releasing a texture view does not touch the surface.
- webgpu.h (webgpu-headers doc/articles/Multithreading.md): native implementations should be thread-safe; everything except the four encoder types may be called from any thread; error scope state is thread-local. wgpu-native keeps one error-scope stack per device (lib.rs `ErrorSinkRaw.scopes`). Haze uses no error scopes (grep).
- DXGI (Microsoft, DXGI overview, "Multithread considerations"): Present may SendMessage to the window's thread during mode changes; the message-pump thread must never wait on the render thread.
- wgpu-native's fatal paths (wgpu-native-fatal-errors.md) abort on whichever thread calls them.
- Upstream status 2026-11-23: wgpu v30.0.2 released 2026-11-12; wgpu-native's newest release is v29.0.1.1, trunk on wgpu-core 29.0.1; PR #630 open, unchanged since 2026-10-12.
- Haze does not set `desiredMaximumFrameLatency` (wgpu default 2; checked 2026-11-04).
