# .hznote: haze-notes' file format

A note is an .hznote: a binfile ([[binfile-and-cachefile]]) with the note's settings in the root and one length-prefixed, checksummed chunk per page; read by name, so changed types load or are refused precisely.

Verified 2026-11-11 against bf4a25f5 plus the uncommitted .hznote work in .claude/worktrees/hznote; the container move and the cache lines re-checked 2026-11-11 against d341d7f0 plus the uncommitted startup work.

- Spec and code: the container is `stdlib/binfile/src/binfile.hz` (its header comment is the byte layout; `CodeSchema` describes the code's types via `traverse.describe`, `binfile.Writer` / `binfile.Reader` are the traverse format). `haze-notes/src/hznote.hz` holds the magic "\x89HZNOTE\n" (`hznoteFormat()`, built byte by byte), `isHznote`, `encodeNote` / `decodeNote` for notes, `encodeShapes` / `decodeShapes` for the clipboard (MIME `application/x-haze-notes-shapes`; a single selected image also goes on as `image/png`, its exact bytes).
- What is stored is what the model's types say (`documents.hz`). Runtime state and caches are `[[binfile.skip]]` (tessellations, hidden, bbox, cachedOutline); `DocumentBody.pages` is `[[binfile.skip="each page is a chunk of its own"]]` and written as chunks. Images hold PNG bytes (`ImageShape.png`), no base64.
- Reading matches fields by name once per file and type (`structPlan`): reordered fields read, unknown ones are skipped (`skipValue`), missing ones take their declared default, none or literal value, else `missingField` refuses. Same name with another kind (i64 vs i32) refuses (`sameKind`). Variants match by struct name (`unionPlan`). Nothing is converted.
- Plain structs (traverse.plainLeafSize > 0, e.g. `Point`, `Vec2`, `Viewport`) are written raw (type layout 1); an array of them is one copy each way when the file's layout is the code's (`identical`). `binfile.plainCopies()` counts those copies (tests).
- Errors are `binfile.Error { problem, message, offset, chunk, path }`; `problem` is NotThisFormat / Newer / Damaged / Incompatible. Every single-byte change and every cut-off length is refused (tests).
- Loading (`persistence.hz`): one step, no frame splitting; `EditorControls.open` runs it in the frame that asks, so a note opened at startup is there in frame 0. The user's 137 notes (206 MB) all open; slowest 35 ms, all 1.1 s, release build (`haze-notes/tests/note-load-bench.hz`).
- Tests: `haze-notes/tests/hznote-tests.hz` (round trips, damage), `stdlib/binfile/tests/binfile-tests.hz` (versions, plain copies, views), `document-load-tests.hz`, `shape-page-tests.hz`; runner `haze-notes/tests/run-test.sh <test> <sources...>`.
- One-time conversion from technicalsketcher's .tsk: `haze-notes migrate-tsk <vault> <backup>` (`haze-notes/src/migrate.hz`, tests `haze-notes/tests/migrate-tests.hz`). It backs the vault up and compares the copy byte for byte, proves every note (written, read back from disk, decoded bit for bit equal, canonical, exported JSON equal to the original tree but for key order, number spelling and the bbox/cachedOutline caches) before deleting its .tsk, stops at the first failure, updates `.hznotes/vault.json`'s lastOpenedFile, then re-proves everything against the backup. Meant to be deleted with the .tsk types once the vault is converted.
- The vault's caches (`.hznotes/vault.hzcache`, `index.hzcache`) hold vault-relative paths since 2026-11-11: a copied vault opens as itself. The old `.hznotes/vault.json` (absolute paths) is no longer read.
